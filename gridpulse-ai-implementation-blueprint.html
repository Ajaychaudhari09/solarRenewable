Executive Summary

GRIDPULSE AI is an enterprise-scale Agentic AI platform that transforms how solar-wind hybrid parks are operated. It ingests sensor data, weather intelligence, historical performance, and grid telemetry — then routes that information through a 24-agent ecosystem to deliver real-time anomaly detection, predictive maintenance, generation forecasting, grid optimization, and natural-language operational interaction via an IBM Granite-powered Operations Copilot.

The platform is architected for the full production vision, but the 48-hour prototype focuses on a tight 12-agent end-to-end chain that is fully functional, demonstrable, and evidences the complete system design to judges.

Problem Analysis
Scattered Assets
Solar + wind installations spread across Kutch & Banaskantha with no unified monitoring layer, causing slow fault detection.
Reactive Maintenance
Equipment failures discovered after the fact. No failure-probability scoring or remaining useful-life estimation.
Weather Blind Spots
Generation shortfalls incorrectly blamed on equipment when dust, cloud cover, or wind shifts are the true cause.
Grid Instability Risk
Sudden solar or wind drops create overload/curtailment events. No automated balancing recommendations exist.
No Financial Visibility
Operators cannot quantify revenue impact of deferred maintenance or the ROI of maintenance actions.
Manual Reporting
Operational summaries require hours of manual data collection; no automated carbon-impact reporting exists.

Core Algorithms & Formulas
Performance Ratio (Solar)
PR = E_actual / (G_poa × A × η_stc)
Underperformance if PR < 0.75 (Warning) or PR < 0.60 (Critical)
G_poa = irradiance on panel surface (W/m²) · A = total panel area (m²) · η_stc = nameplate efficiency
Wind Power Output
P = 0.5 × ρ × A_rotor × Cp × v³
Cp target: 0.35–0.45 · Deviation >15% from power curve = Warning
ρ = air density (1.225 kg/m³) · A_rotor = π·r² · Cp = power coefficient · v = wind speed (m/s)
Failure Risk Score (Predictive Maintenance)
R = w1·age_score + w2·vibration_score + w3·temp_score + w4·fault_score + w5·degradation_score
Default weights: [0.15, 0.30, 0.20, 0.25, 0.10] · R ∈ [0,1]
Scores normalized to [0,1]. Weights tunable per asset type (wind vs solar different defaults).
Anomaly Detection (Z-score)
z = (x - μ_rolling24h) / σ_rolling24h
|z| > 2.0 → Warning · |z| > 3.0 → Critical
Rolling 24-hour window with minimum 12 observations required for statistical validity.
Carbon Impact
CO2_avoided_kg = MWh_renewable × 820 (CEA India grid emission factor 2023)
Additional_CO2_from_maintenance = (MWh_recovered_by_maintenance) × 820
Source: Central Electricity Authority, CO2 Baseline Database for Indian Power Sector, 2023.

Likely Judge Questions & Answers
Q: Why did you build 24 agents instead of just using IBM Granite for everything?
IBM Granite is an LLM — it cannot reliably produce precise numerical forecasts, failure probability scores, or financial calculations. Every critical number in GRIDPULSE AI is produced by deterministic statistical code. Granite handles only what LLMs genuinely excel at: synthesizing structured evidence into human-readable explanations. This is the correct separation of concerns for a safety-relevant operational system.
Q: How is this different from a dashboard with a chatbot?
A dashboard shows data. GRIDPULSE AI acts on data through an agent pipeline. The anomaly detection agent triggers the root cause agent, which feeds the maintenance agent, which triggers the financial impact calculation, which generates a prioritized action recommendation — all automatically, before the operator even opens the dashboard. The copilot then explains why, not just what.
Q: Your data is simulated — is this real?
The sensor data is simulated with realistic statistical properties matching Gujarat solar irradiance (IMD data), Kutch wind profiles (NIWE data), and IEC-standard turbine power curves. The algorithms are real — PR calculation, Z-score anomaly detection, Weibull wind distribution, CEA emission factors. Simulation is the standard approach in energy hackathons where live SCADA access is not feasible within 48 hours.
Q: What would you need to deploy this in production?
Replace simulated sensor feeds with SCADA/OPC-UA integration. Add Kafka for event streaming, TimescaleDB for time-series storage, and authentication. The agent architecture is already designed for this — each agent is a stateless service that consumes and produces JSON, making them independently deployable.
Limitations & Honest Disclosures
Simulated Sensor Data
No live SCADA connection. Data reflects realistic distributions but is not from a real park. Clearly labeled in UI as "DEMO MODE".
Forecasting Accuracy
Linear + Weibull models are sound for prototyping. Production would benefit from LSTM or transformer-based models with longer history.
Failure Probability
Weighted scoring model is explainable and defensible, but a real predictive maintenance model would be trained on actual failure event history.
Grid Optimization
Simplified LP dispatch model. Production grid optimization requires SCADA-connected real-time grid state and certified dispatch algorithms.
